# Ticker（弹幕）行为契约

- 状态：**Ready for review**（Lumen 视觉规格已回填；甘霖 2026-09-12 已定：**出屏优先**、**轨道数不设上限**）
- 日期：2026-09-12
- 上游：`docs/adr/ADR-003-native-behavior-ticker.md`
- 骨架来源：`docs/superpowers/plans/2026-08-18-visual-system-master-plan.md` §5（15 项契约骨架，后续 7 个行为共用）
- 视觉规格来源：Lumen 拾光（2026-09-12）
- 命名：规范 id `ticker`，显示名「弹幕」；`danmaku` 仅作迁移期别名（ADR-002）

## 0. 一句话定义

**弹幕 = 多轨道横向移动的卡片流。**

> Lumen 的性格定调：**堆叠是"到此为止"，弹幕是"顺流而过"。**
> 堆叠留下一个凹坑（位置感、可回头找），弹幕不留痕（不遮挡、看过即走）。
> 弹幕不是"会动的堆叠"，是"不占位的经过"。

> 现状基线（必须对照）：`layout_shelf` 只算一次静态位置，排不下就回退竖排。本契约落地后，`Shelf` 的静态语义**不再是** `ticker` 的实现。**"不动的行叫工具栏，不叫弹幕"**（反面清单第 3 条）。

## 0.1 两个正交的空间概念（实现者务必分清）

| 概念 | 轴向 | 来源 | 含义 |
|---|---|---|---|
| **lane（通道轨道区间）** | 横向 x 区间 | 行为通道分道（`controller.cpp:665-690`） | 该通道独占的横向区间，**不得越界** |
| **band（弹幕带）** | 纵向 y 区间 | 本契约新增（`properties.ticker.band/bandRatio`） | 弹幕轨道整体占据的竖向区域（顶部或底部） |

两者正交：band 决定"弹幕在屏幕的哪一带"，lane 决定"这个通道占哪一段横"。

## 1. 输入模型

| 输入 | 来源 | 说明 |
|---|---|---|
| `card.id` | scene 协议 | 卡片标识 |
| `card.width` / `card.height` | `layout_width/height`，回退 `window.*` | 弹幕卡建议 480×76，见 §2.2 |
| `lane`（x 区间） | 行为通道分道 | 该通道独占的横向区间 |
| `band`（y 区间） | `properties.ticker.band` × `bandRatio` × 工作区高度 | 轨道整体所在的竖向区域 |
| 工作区矩形 | `work_area` | 含 fallback 标记与来源 |
| 行为参数 | **新增** `properties.ticker`（§2） | 速度、轨道、间距、重叠等 |

**参数归属**：全部归**行为/通道**，不归单张卡片（对齐 master plan §3.3：Behavior 管编排、Properties 管数值）。

**命名空间决策（Lumen 建议，采纳）**：动效参数**不塞进 `properties.space`**，新开 `properties.ticker`。

> 理由：`space` 是"卡片摆在哪"的**静态几何**；`ticker` 是"卡片怎么动"的**时间参数**。混在一起后面结算轨道会互相污染。

## 2. 参数定义（Lumen 定稿）

| 字段 | 类型 | 默认 | 范围 | 说明 |
|---|---|---|---|---|
| `direction` | enum | `left` | 锁 `left` | 右→左；文字左移保持正立可读 |
| `speedPxPerSec` | int | **400** | 150–800 | 见 §2.1 |
| `band` | enum | `top` | `top` / `bottom` | 弹幕带在屏幕上半还是下半 |
| `bandRatio` | float | **0.28** | 0.15–**1.00** | 弹幕带占工作区高度的比例（放开到可满屏） |
| `trackCount` | int | **0**（auto） | **不设上限** | 0 = 按 band 高度自动算 |
| `trackGapPx` | int | **8** | 0–48 | 异轨纵向间距；轨道高 = 卡高 + trackGapPx |
| `minGapPx` | int | **64** | 24–160 | 同轨最小水平间距 |
| `hoverPause` | `on/off` | **`off`** | — | 沿用既有 `interaction.hoverPause`；语义见 §6 |
| `overflow` | enum | **`avoid`** | `avoid` / `queue` | 见 §4 |
| `heartbeatMs` | int | **16** | 16 / 33 | 60fps 默认；30fps 备选 |

### 2.1 速度（两条硬约束）

- 默认 **400 px/s**，范围 **150–800**。换算：≈ 每 **4.8 秒**穿过一个 1920 宽的屏。
  - 理由：480px 的卡在 400 px/s 下视野内停留 ≈6.0s，读"1 行标题 + 1 行正文"绰绰有余；800 px/s 停留 3.0s 仍可读，是"更弹幕"档；**低于 150 会读成"卡死"**。
- **硬约束 ⚠️：位置必须是时间的纯函数**
  `x(t) = x0 − speed × (t − spawnT)`
  **禁止**用"每帧累加位移"实现。心跳可能抖动/丢拍，累加会漂移和跳变。

### 2.2 卡片尺寸

- 弹幕卡建议 **480 × 76**（`aspectRatio: wide`），**不复用** medium 的 420×220。
  - 理由：220 高会直接吃掉轨道条数；弹幕卡只需"标题 1 行 + 正文 1 行"，76px 刚好。
- **约束**：弹幕卡内容锁 **1 + 1 行**。高矮不一会把轨道线撑乱，节奏就没了。
  - ⚠️ **与种类轴的交互（待定）**：`typography` 模型里有 `titleLines/bodyLines`，UI 已收敛掉入口。需明确"1+1 行"是 ticker 行为的强制约束，还是预设值。**不静默二选一。**

### 2.3 轨道高度与轨道数

- 轨道高 = 卡高 + `trackGapPx`。默认 `trackGapPx = 8` 时，76 高的弹幕卡轨道高 = **84**。
- **按高度算，不写死条数**：`trackCount = clamp(floor((bandH + 8) / 84), 1, 4)`，`bandH = workArea.height × bandRatio`。
- 1080 高屏算例：`bandH = 302` → `floor(310/84) = 3` 条。
- **不设条数上限**（甘霖 2026-09-12 明确决策：「上限不要四条，不要上限，我就喜欢满屏弹幕」）。下限仍为 1 条。
  - Lumen 原建议 1–4 条，理由是"超过 4 条会跨过屏幕中线，'余光扫到'变成'占屏'"。该理由**保留为默认区间的依据**（默认 `bandRatio: 0.28` 时约 3 条），但**不作为硬上限**。

### 2.4 同轨间距

- `minGapPx = 64`（**不是**现有的 8/12）。
  - 理由：弹幕两张卡之间要能"切开"；64px ≈ 4 个字宽，够眼睛读成两条独立信息，低了会连成一整条跑马灯。

### 2.5 心跳（新增架构能力，ADR-003 §2）

- 有 ticker 卡在动：**16ms（60fps）**；**无 ticker 卡：停跳（0）**。
- 低功耗备选 **33ms（30fps）**。
  - 理由：`SetWindowPos` 是每帧每卡一次系统调用，≤4 张弹幕卡时 60fps ≈ 240 次/秒，可接受；30fps 下 400 px/s 每帧跳 13px，中文小字会看出阶梯感。
- **空闲必须归零**——心跳是"只在需要时跳"的能力。

## 3. 进入规则

- 卡片初始位置：**完全位于进入侧屏外**（`entrySide=right` 时 `x = lane.right`），纵向落在分配到的 band 与轨道。
- 进入即开始移动，无等待（除 §3.3 的排队延迟）。
- **判定**：创建瞬间快照中，卡片与 lane **无交叠**；下一 tick 后交叠。

## 4. 轨道分配规则（Lumen 定稿，可判定）

**规则：选"进屏点净空最大"的轨道；并列取最上面那条。**

判定式（新卡左边缘进屏点 `E = lane.right`，需 `prev.right ≤ E − newWidth − minGap`）：

1. 对每条轨道算 `clearance = E − (prev.right + newWidth + minGap)`，取**最大值**的轨道。
   - **没有卡在前方的轨道，`clearance` 记为 +∞，一定优先。**
2. 并列时取 **track index 最小**（最上一条）——保证可预测、不随机。
3. 若所有轨道 `clearance < 0`（全被占），取 `clearance` 最大者，**延迟 `(−clearance)/speed` 秒后再放行**；**不换道、不叠放**。

> **为什么不是"选卡最少的轨道"**（Lumen 推演结论）：
> 等速弹幕一进屏，相对间距就被冻结了，之后永不追尾。所以"卡最少"的轨道可能刚好有一张**刚进屏的长卡**，反而最危险。
> **判据只能是"进屏点前方的净空距离"，不是"轨道里的卡片数量"。**

- **判定**：构造"某轨道只有一张刚进屏的卡、另一轨道有两张旧卡"的用例，新卡应进**前者之外**的轨道（净空更大者）。

## 5. 并行规则

- 多轨道**完全并行**：任一卡片的移动、关闭不改变其他轨道的计算。
- 通道间**完全隔离**：一个 ticker 通道的布局/淘汰不得影响其他通道（沿用既有隔离语义，回归红线）。
- **判定**：同时创建 N 张卡，关闭其中一张，其余卡片的 `x(t)` 轨迹不变。

## 6. 冲突／避让规则

| `overflow` | 行为 | 判定 |
|---|---|---|
| **`avoid`（默认）** | 不叠放：无净空时**延迟进屏**（§4.3），进屏后等速不再调整 | 全程任意时刻同轨两卡间距 ≥ `minGapPx` |
| `queue` | 排队等待，按序放行 | 放行顺序与进入顺序一致 |

> **默认选 `avoid` + 延迟进屏，而不是允许重叠或丢弃**（Lumen 理由）：
> 两张独立 Win32 分层窗口叠在一起 = 视觉上糊成一坨，"弹幕能叠"本身就是**假承诺**（重叠的弹幕读不了）；
> 而丢通知（`dropOldest`）违背"看得见的就是真的能用的"——**通知不该因为排不下就消失，宁可晚 1 秒进屏。**

- **判定**：构造轨道全满的用例，新卡**不叠放、不消失**，而是延迟后进入。

## 7. 容量与溢出规则

- 容量单位是**通道**（`maxVisible`）。
- ⚠️ master plan §3.2 的立场是**默认不抑制通知风暴**（默认 `maxVisible: 1000`）。本契约**不改变该默认值**——弹幕天然可容纳更多，但不是擅自改默认值的理由。
- 通道内排不下时，按 §6 的 `overflow` 处理（默认延迟进屏，不丢弃）。
- **判定**：超出容量时，被淘汰卡片与通道指标（`suppressed`）一致，且不残留窗口。

## 8. 生命周期

```text
屏外进入 → 匀速穿越 → 完全离开出口侧 → dismiss（reason = 出屏）
                     ↘ 用户关闭 / 超时 → dismiss（reason = 既有原因）
```

- **出屏判定**：`card.right < lane.left − 24`。
  - **24px 缓冲是硬要求** ⚠️：防止窗口阴影/圆角被边缘"切一半"留在屏上——**收尾必须干净**（反面清单第 6 条）。
- **判定**：卡片消失前一刻，其矩形与 lane **无交叠**；`dismiss` 的 card id 与预期一致。

## 9. 关闭方式

- `dismissMode`（`closeButton` / `anywhere` / `timeout`）**语义不变**，由既有卡片窗口逻辑处理（`runtime/scene/window.cpp`）。
- 用户关闭 → 立即出场并清理，不等出屏。
- **已定（甘霖 2026-09-12）：出屏优先。** 卡片一旦完全出屏即回收，`timeout` 不再对已出屏的卡片生效；`timeout` 仅在卡片尚未出屏时先行触发关闭。
  - 理由：避免"卡片已划出但计时器还在"的空转。

## 10–12. 入场／持续／出场钩子

| 钩子 | 触发点 | 现状 | 本契约要求 |
|---|---|---|---|
| 入场 | 卡片进入 lane | `effects.slots.enter` 已有 | **不做整体淡入**（本来就在屏外）；但在入口 **120px** 内做 `0→1` 透明度渐入（`enterDurationMs: 200`），避免窗口在边缘"啪"地出现 |
| 持续 | 每 tick | **不存在**（见 §2.5） | 新增 tick 点；`effects.slots.idle` 挂此处 |
| 出场 | 出屏或 dismiss 前 | `effects.slots.exit` 已有 | **不淡出**，出屏即回收（省一次渲染）；出场特效不得延迟清理超过 `exitDurationMs` |

- **判定**：三个钩子的启用/关闭组合下，卡片都能正常结束，不出现"钩子开着就不消失"。

## 13. 悬停（Lumen 定稿）

- **默认 `off`（不暂停）**。
  - 理由：通知是"看过即走"的东西，鼠标无意压在上面就被扣住，观感像卡死；且卡片是独立窗口，悬停检测本身要额外追踪。
- **若开 `on`**：必须是**整条 ticker 通道级冻结**（所有轨道一起停），恢复后从冻结位置**续走、不跳变**。
  - 理由：只暂停单卡会让后面的卡追尾——那不是"暂停"，是制造事故。

## 14. 压力测试

沿用 master plan §5 对 Ticker 的必验项，逐条要有可判定条件：

| 场景 | 通过条件 |
|---|---|
| 多轨并行 | N 条轨道同时有卡，互不干扰 |
| 不同速度 | 不同速度卡片同轨时，行为符合 §6 |
| 轨道不足 | 全满时**延迟进屏、不叠放、不丢弃**（§4.3 / §6） |
| 长时间风暴 | 持续高频创建，稳定运行不崩溃、不累积泄漏、CPU 可接受 |
| 出屏清理 | 全部卡片最终出屏且**无窗口泄漏** |
| 心跳空闲 | 无卡片时心跳**停摆**，CPU 无可测上升 |

## 18. 性能风险（"满屏弹幕"偏好的直接代价）

**不设条数上限 + 默认不抑制风暴（`maxVisible: 1000`）= 可能同时动画大量独立窗口。**

- 每张卡片是一个独立 Win32 分层窗口，每 tick 一次 `SetWindowPos`。60fps 下 N 张卡 ≈ `N × 60` 次系统调用/秒。
- 量级感受：12 条轨道 × 每条 4 张 ≈ 48 张 ≈ **2880 次/秒**；满屏叠加风暴时数字会显著更大。
- **不预先优化，但必须测量**：压力测试需记录"卡片数 → 帧时间 / CPU"，并给出可接受拐点。
- **候选缓解手段（不在本契约定稿，留待实现决策）**：
  1. 自适应心跳：卡片多时降帧（代价：Lumen 指出的阶梯感）
  2. 单窗口批量渲染：把弹幕画进一个全屏分层窗口内的多张卡片，而非 N 个窗口（**架构级改动**；满屏场景下效率高一个量级，代价是关闭按钮/命中检测要自己实现）
  3. 只对"视野内"的卡片做位置推进
- ⚠️ **这一条是"满屏弹幕"的直接代价，不是可以忽略的细节。**
