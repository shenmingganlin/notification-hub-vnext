# ADR-004：ticker 采用独立渲染后端（覆盖层画布），stack 保持窗口路径

- 状态：Accepted（实现落点见 ADR-010：合成器精灵，不按帧重绘整张表面）
- 日期：2026-09-12
- 关联：ADR-003（其红线要求 `stack` 不可改变）、`docs/superpowers/specs/ticker-behavior-contract.md` §2.3 / §18
- 触发：甘霖 2026-09-12 明确要求 ticker 具备「最好的性能」，并偏好满屏弹幕、轨道数不设上限

## 背景

**现状成本模型**：每张卡片是一个独立 Win32 分层窗口，位置由 Native 计算后 `SetWindowPos` 施加。

每帧推进 N 张卡 = **N 次 `SetWindowPos` + N 个窗口的 DWM 合成**。若卡片**内容**也随帧变化（契约 §10 要求入口 120px 内做透明度渐入），还需 `UpdateLayeredWindow` 上传整张位图。

**数量级**（契约 §18）：

| 场景 | 卡片数 | 每秒窗口操作 |
|---|---|---|
| Lumen 默认带（3 轨） | ~12 | ~720 |
| 满屏（12 轨） | ~48 | ~2,880 |
| 满屏 + 风暴（默认不抑制） | 数百 | 上万 |

**结论**：以「一卡一窗口」承载满屏弹幕，成本随卡片数**线性上升**，且内容动画额外触发位图上传。这与「最好的性能」直接冲突。

## 决策

### 1. ticker 使用独立渲染后端：覆盖层画布

每个 ticker 通道使用**一块幕布 HWND**。卡面是纹理；位移是合成器偏移。具体落点见 ADR-010，不以「每帧重绘整张表面」为主路径。

- **优势**：每帧成本与卡片数**解耦**（一次绘制/提交，而非 N 次窗口移动），可支撑满屏与风暴。
- **代价**：卡片命中检测、关闭按钮、拖拽需在画布上自行实现（不再是每个窗口自带的消息处理）。

### 2. `stack` 保持现有窗口路径不变

这是 ADR-003 的红线。stack 是回归基线，本次**不动它**。

### 3. 行为逻辑与渲染后端分离

位置是时间的纯函数（契约 §2.1），行为层产出 `(cardId, x, y)` 列表；「把结果应用到屏幕」是一个**可替换的步骤**。

- 两种后端共享同一套行为语义（轨道分配、避让、出屏判定）。
- 允许未来把 stack 迁到画布而**不动行为逻辑**。

### 4. 卡片绘制代码复用

抽出「把一张卡片画进任意渲染目标（可带偏移）」的例程，两条路径**共用**。

- 目的：防止 stack 与 ticker 的卡片视觉随两条路径**分叉**（甘霖对视觉一致性敏感）。

## 后果

- **收益**：ticker 性能与卡片数解耦；行为逻辑只有一份；stack 零风险。
- **成本**：新增一条渲染路径；窗口层需新增覆盖层的输入处理（命中检测 / 关闭 / 拖拽）。
- **风险**：
  - 两条路径的卡片视觉不同步会分叉 → 由决策 4 缓解
  - 覆盖层的点击穿透语义需与桌面其他窗口协调
- **未决（由实测决定）**：覆盖层是否需要升级到 DirectComposition / D3D。分层窗口的 `UpdateLayeredWindow` 每帧上传整张位图，若覆盖层面积大、帧率高，这一项会成为新瓶颈。**届时以实测数据为依据，不提前重写。**

## 明确不做

- 不在本次统一 `stack` 的渲染路径（红线）。
- 不为尚未验证的瓶颈提前做 D3D / DComp 重写。
- 不改变既有 `scene.*` 协议语义。
